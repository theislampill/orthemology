# Sixteenth Orthemology: source and verification evidence

This archive collects the public source packages, replay instructions and verification records for the Sixteenth Orthemology research. Completion, publication, canonical adoption and successor status are established separately.

Start with `VERIFICATION_GUIDE.md`. The main report and editable mathematical companion are delivered separately; their identities are bound by the public maps. The companion's public reader text supports inspection of its native-mathematics mapping. No second main-report reader text is included.

## Contents

- `proof-core/`: the immutable recovered 111-module source archive and its detached author/independent verification records.
- `core-source-build-assurance/`: detached qualification of the exact required third-party source closure, followed by a complete unchanged core replay. Official toolchain components remain trusted.
- `signed-service/`: the separate immutable 95-predecessor-plus-21-new-module signed-controller source archive, detached verification ZIP and release identity. “Signed” means positive/negative certification.
- `empirical/`: the accepted source-only replay payloads in a new recovery-time ZIP container, synthetic-test evidence and digest/status-only records for the complete fresh replay.
- `occurrence/`: the approved historical four-file public fixture and its historical member manifest. Consult its own README for interpretation and limits.
- `maps/`: public source locators and mathematical-reader bindings. Original-input hashes do not imply that those original inputs are redistributed.
- `verify_bundle.py` and `BUNDLE_MANIFEST.json`: offline file identity, exact file census and safe ZIP extraction. This utility executes no proof, empirical analysis or fixture.

The two proof archives are separate packages with overlapping ancestry. Their module counts must not be added as though they were disjoint, and the signed extension is not part of the immutable 111-module archive.

All accepted inner archives are preserved byte for byte. Historical build paths in technical receipts are provenance, not required installation locations. No raw third-party paper or data, participant-level record, primary wording, private source assessment, internal coordination material, credentials or memory notes is included.
