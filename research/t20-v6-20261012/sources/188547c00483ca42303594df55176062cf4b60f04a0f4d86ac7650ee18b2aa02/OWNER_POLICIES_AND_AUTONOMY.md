# Owner workflow and standing execution boundaries

This section consolidates owner statements from the original Orthemology and T20 conversations. It is not a new permission to act on their behalf.

## Core development cycle

1. Acquire and inspect the actual project/current source state.
2. Identify a specific idea, concern, gap, diagnosis, proof obligation or candidate improvement.
3. Brainstorm, adversarially criticise, and wayfind toward a precise bounded change.
4. Write a **RLGWO — Research-Lab-Grade Work-Order** with named owner, target, scope, invariants, dependencies, evidence and acceptance criteria.
5. Execute only authorised work, including tests and negative controls.
6. Independently review actual new work, source bindings, currentness and evidence.
7. Merge only after the owner specifically authorises it. Treat that verified admissible project improvement as a **GDOPL — Gradient Descent Over Project Lagrangian** step.

Filing a work order or writing a change proposal is not execution, a PASS result or release permission. A PR can be technically mergeable yet still lack semantic/currentness review or owner acceptance.

## CBAL / DAG execution

**CBAL = Closure-Bound Auto-LOOM.** For governed RLGWO DAG orchestration, optimise *whole-cell evidence-verified exits per total execution cost*, not worker activity or number of parallel subtasks. A READY node isn't automatically DISPATCHABLE: identify the closure predicate, evidence, downstream reviewer/JOIN/native capacity and all relevant shared prerequisites first. Don't generate unlimited parallel work with no path to final closure. This policy applies in the owner's wider engineering workflows (ImplementAudit, Salah Widget) but is **not** an instruction to turn an open-ended philosophical research programme into an artificially closed finite engineering DAG.

## T20 research autonomy and continuing conduct

- Dot has standing authorisation to pursue substantive reading, mathematical deductions, countermodels, proof checking, source comparisons and cross-domain mappings *during active execution*. It can critically reject inherited positions rather than agreeing to satisfy the owner.
- T20 remains OPEN pending owner adjudication. The original six-hour active-research floor lacks historical certification; do not count waiting, packaging, manifest checks, wall-clock time or a closed PR as research hours.
- A finished proof, an inaccessible source, a saved checkpoint and a local exhausted subproblem are **not** reasons to terminate the full scientific programme. Choose another consequential feasible frontier or state the genuine operational inability to continue in that session.
- No assistant can honestly claim it conducted research while execution was inactive unless there is a separately authorised running task. Explain actual execution limits without pretending continuous background agency.
- Scientific initiative does not authorise editing protected repository state, unapproved spending/commitments, creating large unrequested compute campaigns, or claiming owner acceptance.
- Adversarial work should tackle a **specific surviving serious objection** to an accepted or actively supported premise; endlessly revisiting alternate philosophers after their local issues are understood isn't a productive substitute for affirmative foundations.
- Prefer a discriminating operation (a proof, countermodel, source rereading, broken map, repaired theorem, meaningful negative control) over another project-wide summary or an AI reviewer agreeing with its own upstream model.
- Negative results, corrected mistakes, failed transports and uncertainty must remain in the record with their original evidence statuses. A later stronger status supersedes but doesn't rewrite an earlier checkpoint's point-in-time record.

## Source, formal and acceptance discipline

- Preserve source bytes and original archive identities; do not infer later checkpoint PASS from ancestor CI or from a file title.
- A Lean kernel proof can establish a formal typed statement with explicit axioms; that is distinct from an ordinary written analytic proof, Python exact tests, historical-source interpretation and actual-world warrant. **Internal AI independent review ≠ unexposed external specialist replication.**
- Don't silently treat retained moments as a genuine law, a projection as a globally faithful representation, a typed identity as raw-code identity, numerical descent as cognitive knowledge, or an accessible report as authenticated transmission.
- The owner prefers UK spelling in formal documents and concrete actions, with one-shot terminal workflows when appropriate. Seek explicit approval for auto-editing. Previous permission to install Lean 4.19.0 and relevant dependencies should not trigger gratuitous reinstalls.
- Before using the public GitHub state, refresh exact base/head/main/CI and understand whether a source package's content is on main, a PR, or an unpublished research checkpoint.

## What a productive new chat can do

Read the handoff's summaries, then inspect the exact relevant source archive rather than demanding that the owner paste 100 separate checkpoint histories. Do not declare every archive read just because an index exists. If the user requests independent proof scrutiny, isolate a small theorem and verify its assumptions; if they request a Dot handoff, send only the material new to Dot and distinguish a recovery archive from authored research.
