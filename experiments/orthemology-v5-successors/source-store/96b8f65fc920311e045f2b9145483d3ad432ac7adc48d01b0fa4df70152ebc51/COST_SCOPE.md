# Ordinary verification-cost scope

This is an ordinary bit-cost argument for the specified finite AST implementation, not a Lean complexity theorem. No cost semantics or machine-refinement theorem is claimed.

Input q,n,k are natural dimension claims, with q,n,k all required positive. `Input.inputCheck` first evaluates `Shape`: positivity; actual row and priority array lengths; actual coding-list lengths. Only after this short-circuit gate succeeds does it enumerate `Fin q`, `Fin n`, or `Fin k`. Thus an enormous binary dimension with tiny submitted vectors, including any zero-dimension product trick, rejects without carrier enumeration. Multiplying the dimension headers and comparing lengths has polynomial bit cost. Accepted dense input has at least q*n*k*n rational entries and q*n*k priorities, so every carrier loop is charged to actual explicit input length.

Sparse menus are literal finite lists, with empty default. Keys and member ranges are checked and duplicates reject. Lookup scans this list and compares the actual support indices; no function table over all supports is constructed. Nodes likewise scan only submitted supports. Ordered-key validation checks the listed cardinalities and canonical increasing support-index masks. It does not enumerate omitted supports.

Checking traverses every submitted node and every listed state/candidate obligation. Pair safety examines every possible next observed state and all live models, computes its exact live support, and scans the submitted body for the matching smaller support. Path checking reconstructs the current source and examines each actual submitted edge. Components check submitted pair inclusion, their internal successors, explicit root paths, candidate-positive successor closure, and full numerical rows for every live rival. The attained even-minimum check searches only the supplied component pairs, never all subsets or a numeric priority range. Naive repeated membership and linear scans increase polynomial degree but remain polynomial in the explicit table and AST lengths.

All rational entries are exact normalized Lean rationals. Addition/comparison use integer arithmetic charged at numerator/denominator bit lengths. A row sum's denominator can be bounded by the product of its explicitly supplied denominators, whose bit length is the sum of their bit lengths. Numerator growth is likewise polynomial in total row encoding length. Support-key representation has polynomial bit length in the validated model dimension. Priorities are only compared and reduced modulo two, never used as exponent or loop bounds. Finite syntax may be exponential in the number of hidden models; there is no polynomial certificate-size claim or synthesis lower bound.

The optional bound envelope compares actual input arrays, menus, codings and interpretation fields before fresh checking. String lengths and input comparison count. Equal digests are not used to prove equality. A fresh irrelevant input change may remain valid, while a stale envelope is rejected.

Lean/compiler/Mathlib arithmetic and finite-container implementations are trusted as the execution substrate. The dependency audit includes `implemented_by` redirections and reports trusted external primitive leaves. `#eval` and generated C evidence establish the tested Lean computation/codegeneration endpoint. They do not establish parser correctness, linked standalone deployment, verified binary cost, or physical execution safety.
