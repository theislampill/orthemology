# CV-O — A small revision-sensitive operational calculus

Status: ordinary proof and explicit refinement specification. The v4 Lean plan
model is preserved but uncompiled. This is not a proof of the entire Python
implementation. Internal All/self-instantiation is retained, not replaced.

## 1. Fixed foundation K
Choose interface names I and a value interpretation V_i for each i∈I. Choose
primitive arrows p:i→j with partial interpretations ⟦p⟧:V_i⇀V_j and a finite,
structurally checked plan language generated by identity, primitives,
composition, products/projections and a finite typed-source certificate node.
The native finite fragment contains successor, iszero and Boolean negation;
source nodes contain certificates of a realisability arrow A⇒B.

Use partial interpretations to represent declared resource failures. For example,
a bounded natural interface can contain integers below 2^256 and successor can
refuse its maximal argument. A successful result must still have the codomain
type. Do not equate this with total execution of every ambient Lean function.

A structural checker checks primitive tags and their interfaces, matches the
intermediate interfaces of composition, and verifies source-certificate syntax
by the finite derivation rules. It collects dependencies as the union of child
read sets plus the rule keys controlling the constructor. A source node is
accepted only after an actual derivation certificate is checked, not from a
Boolean claim that one exists. Proof by induction on finite source derivations
supplies semantic arrow membership. This is the ordinary FiniteBridge argument,
not a new checker-soundness axiom.

By induction on the plan, a successful interpretation preserves its interface.
The source case uses application of a realised arrow to a realised argument;
composition uses the induction hypotheses and interface matching. Primitive
cases are the explicit successor/iszero/negation computations. This is the
nondefinitional soundness step behind the operational wrapper.

K consists of this syntax, checking and interpretation machinery and the rules
for evidence transport. It stays fixed. Nothing below revises its logical axioms,
universe rules, or the realisability interpretation.

## 2. Contexts and dependency locality
A context Γ is a finite map from keys k to (version v_k, value w_k), with stable
defaults for absent entries. Values record enabled permissions, active predicate
vocabularies, declared observation laws/maps and risk obligations. Version values
are natural numbers with no wraparound.

Checking an accepted finite candidate c reads finitely many keys D(c,Γ), returning
its checked plan and, where required, a finite law/signature certificate. The
checker must satisfy dependency locality:

    if Γ' agrees with Γ on every captured key/value/version in D,
    the same candidate obtains the same result and semantic obligations.

This is an obligation about the checker algorithm, not true of every checker.
Structural induction proves it for the declared grammar if child dependencies
are unioned and all branch-selecting reads are recorded. In particular:
- an absent optional obligation is a READ and has a captured guard key;
- enumeration of all active predicates reads the vocabulary-version key;
- discovering a new nested dependency reads the key whose value names it.

An untracked negative lookup is a counterexample: an old admission can pass
when no risk rule exists, and become unsound after adding that rule under a key
it never recorded. The `need:*` and vocabulary guards in the concrete engine
are necessary to the locality proof.

A revision touches a finite set T. Every touched key receives a strictly larger
version, even when its value is unchanged. Untouched keys preserve both value
and version. A bounded implementation must refuse version exhaustion, not wrap.

## 3. Evidence, licences and executable projection
Issuance stores an immutable record

    (candidate bytes, checked plan, dependencies D, captured stamps b,
     certificate evidence, issuer identity)

under a fresh ticket in a registry. Licence possession is the pair (issuer,
ticket). The validity algorithm checks issuer identity, registry lookup, captured
key coverage, enabled permissions and equality of every current dependency stamp
with b. A record is issued only after successful finite checking; empty or
reject-all checking therefore cannot satisfy the positive clauses below.

Dispatch performs validity checking and interpretation at one revision-consistent
state. This can be a single-process lock, or a separate formally justified
transaction protocol. No distributed protocol is assumed here.

The executable projection of Γ and its registry enumerates the currently valid
ISSUED records, with their interfaces. It does not enumerate all semantically
valid programs, infer new permissions, or turn a stale snapshot into authority.
A call from a projection still passes dispatch validation.

## 4. Exact licence-transport theorem
Fix a licence actually issued at Γ_0, with issuer, ticket and immutable registry
record unchanged, and suppose every revision follows the strict-version rule.
Let T_j be the keys touched between Γ_{j−1} and Γ_j. Then

    valid(Γ_n,licence)
      iff ∀k∈D, stamp_{Γ_n}(k)=stamp_{Γ_0}(k)
      iff D ∩ (⋃_{j=1}^n T_j)=∅.                      (O-transport)

Proof. The first equivalence follows from the explicit validator plus issuance:
coverage and initial permission checks were established and equal stamps preserve
them. For the second, untouched keys preserve stamps by induction. Any touched
captured key strictly increases its version and subsequent revisions cannot
restore the old version, regardless of whether the values revert. ∎

This proves both irrelevant-revision preservation and relevant-revision
invalidation. It is stronger than comparing only permission booleans: enabling,
disabling and re-enabling cannot revive an old licence (ABA resistance).
The theorem assumes the issued record persists. Explicit ticket deletion or
issuer change independently invalidates it and must be added to the right side
if those operations are included in the revision language.

An operation already holding the dispatch lock can finish before a revision
linearises. Once that revision has linearised, subsequent dispatch with the old
relevant licence fails. This is the exact concurrency meaning; the theorem does
not revoke a computation retrospectively after it has already run.

## 5. Nonvacuity, composition, permission changes and source connection
Use a context enabling the successor, iszero, negation and composition rules.
The checker accepts successor and dispatch sends 2 to 3. iszero distinguishes
0 and 1. Negation after iszero is a useful checked composition, with dependencies
equal to the union of the two children plus its composition guard.

A context with successor disabled rejects its candidate. Enabling it under a new
version adds an admissible operation; issuing and dispatching a fresh licence
performs the transformation. Disabling it invalidates that licence and fresh
admission. Re-enabling permits new admission without reviving the old licence.
These are explicit constructive witnesses, not properties of a reject-all engine.

In the source semantics let C be conversion-invariant predicates on raw programs
and All(B)=⋂_{A∈C}B(A). This is again in C. Its uniform program can be instantiated
at any A∈C, including All(B). The finite source identity certificate can be
instantiated at its own finite type code and applied to itself, producing I I→I.
A source operation takes this checked arrow certificate and an argument
certificate and constructs/checks the application certificate. It therefore
connects to real internal polymorphic computation, not an arbitrary `realizedBy`
field or an external-only product. It still does not make C itself a full
same-level universe of all ambient types.

Reach is the algebra of finite, well-formed, resource-admissible plans generated
by the selected primitive and certificate interfaces. The universe-polymorphic
Lean copy schema represents any supplied type at each universe level, but this
is not a proof that arbitrary ambient Lean functions are parametric, serialisable
or reachable through the finite JSON engine.

## 6. Refinement debt and authority transport
Suppose the captured evidence for a plan includes a law ν_0, observation map,
full-event-repertoire interpretation, and bound d(ν_0)≤ε. Along a finite measurable
refinement chain, CV-R proves

    d(ν_n)≤ε iff Σ_{j=1}^n Δ_j ≤ ε−d(ν_0).

At an infinite full observation it proves the same with the additional residual
J. This determines semantic survival of the BOUND. It does not override
O-transport: a relevant vocabulary/law revision invalidates the old licence.
Reissue may use an explicitly checked transport certificate containing the map
factorisations, laws and increments, bound to Γ_n. An algorithm for a restricted
law grammar can check this; arbitrary productive observers cannot have a complete
effective zero-defect certifier by CV-C. Context policy can also explicitly change
ε, but that proves a different requirement, never the old bound by stealth.

The nonzero-defect laws concern the declared observation outcomes, which may be
infinite streams or continua. They are NOT probability laws on the unchanged
countable set of finite realiser terms. Interpreting all measurable events as
source types would require a separate adequacy theorem not supplied here.

Thus operational authorisation and semantic validity are distinct judgments,
with an explicit rule connecting them rather than a single overloaded "pass".

## 7. Girard-sensitive full sections remain an independent capability
Define a purported SCUU capability through independently meaningful operations:
a small carrier U at the stated universe level, represented dependent products,
operational abstraction and application handles total on every ambient section,
and a beta equation on their returned values. Such a capability extracts maps

    pi : (Type r → Type r) → Type r,
    lam : (∀X,A X) → pi A,
    app : pi A → ∀X,A X,
    app(lam f)X=f X.

The preserved Girard/Hurkens theorem derives False from that bundle. The v4
OperationalBoundary source instead packages the specific diagonal family and
extracts its preserved no-retraction boundary; the two paths are kept separately
identified. The standalone project additionally imports the pinned upstream full
package theorem for a direct cross-check. Neither path is newly kernel-verified.

The positive operational wrapper does not supply lam for arbitrary ambient
sections; it admits checked finite programs. Internal All, its code and its own
instance remain available. These positive and negative facts are independent
and may be conjoined without identifying internal self-instantiation with the
stronger SCUU capability.

## 8. Generic-wrapper consequence: an adversarial novelty test
Nothing in Sections 2–6 needs a special new foundational axiom. ANY realisability
model with a sound finite executable fragment and adequate primitive examples
can be given the same versioned dependency/registry wrapper. By structural
induction it inherits interface preservation and by natural-number monotonicity
it inherits O-transport, without changing its type semantics.

Therefore the bare conjunction

    useful revision-sensitive execution + internal impredicativity
      + absence of the full Girard package

is a modular application/integration result, not evidence of a new foundation.
An existing richer realisability model can receive the same wrapper. An exact
prior implementation need not have used our vocabulary for this novelty rebuttal.
The quantitative revision certificate and its computability limits are the more
specific research targets.

## 9. Concrete v4 map and exact refinement gap
- `Engine._compile`: finite structural plan checking and dependency collection.
- `admit_json`: strict parsing, immutable canonical source, evidence calculation,
  issuer/ticket registration and captured version bindings.
- `_current`: current dependency stamps; absence guards are included.
- `dispatch`: lock-scoped validation, input checks, evaluation, intermediate and
  output bounds; no relevant revision interleaving inside the lock.
- `revise_rule`, observation/vocabulary/obligation revisions: strictly bumped keys.
- `project`: current registered licences, not an enumeration of all programs.
- `core` plan: actual finite source proof checker and application certificate.

The code inspection and new finite trace comparison instantiate O-transport for
native rules and the tested source/law fragments. Exact engine API method names
and tested inputs are in experiments/, not guessed from this mapping.

Remaining: a mechanised simulation of Python parsing, bounded substitution,
exception handling, registry/issuer identities, Python locks and rational-law
checking into this abstract system. The existing Lean plan model is total and
omits several of those mechanisms; successful-execution correspondence for bounded
values is not whole-runtime equality. None of these gaps is closed by a passing
finite trace census or by the ordinary theorem about the abstract structure.
